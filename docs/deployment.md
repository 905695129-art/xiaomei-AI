# Heart Studio 部署指南（Docker Compose）

本指南提供可自行托管的容器部署方式。**它不会自动替你购买服务器、配置域名、创建 Resend 发件域名或开通支付商户。** 首次上线仍需要你控制的服务器、域名和服务商账户。

## 中国大陆上线要求（本项目默认目标市场）

Heart Studio 的默认部署、产品文案、支付链路和数据处理应以**中国大陆用户**为目标设计。GitHub Pages/Floot 海外预览仅用于开发演示，不代表已具备中国大陆正式运营条件。

### 域名、备案与部署地域
- 正式域名应使用可在中国大陆正常访问的域名；使用中国大陆境内服务器提供互联网信息服务时，按主管部门要求完成 ICP 备案。若实际业务属于经营性互联网信息服务，需先评估是否应取得增值电信业务经营许可证（常称 ICP 许可证），不能把ICP备案等同于经营许可。
- 正式上线前由运营主体确认业务分类、主体资质、备案/许可要求、公安联网备案等适用义务；不得先收费后补手续。
- 优先选用中国大陆云厂商和境内地域的计算、数据库、对象存储、CDN及日志服务。逐项记录数据存储地域、备份地域、运维访问地域和服务商子处理者。
- 当前邮件方案 Resend 不能默认视为适合大陆生产环境。应评估境内邮件/短信服务商的可达性、实名/签名/模板要求、数据处理条款和日志地域；在完成真实送达测试与合规评估前，不开放依赖邮件的注册验证和找回流程。
- 正式域名、HTTPS、备案信息及隐私政策中的运营者名称、联系方式必须一致并真实有效。

### 个人信息与内容治理
- 按《个人信息保护法》《数据安全法》《网络安全法》及适用配套规则完成个人信息清单、处理目的/依据、最小必要字段、保存期限、访问权限、删除/导出流程和个人信息保护影响评估（适用时）。
- 默认采用境内存储和境内服务链路；如任何个人信息被境外云、邮件、分析、客服或运维服务接收/访问，先识别数据出境场景并依法履行告知、单独同意及适用的数据出境合规程序，不得仅因服务商提供“加密”就认为合规。
- 情侣互动可能涉及私密留言、照片、关系状态等高敏感场景。默认私密、按需授权、明确撤回/删除入口；不要把私密关卡内容放进公开分享页、日志、分析事件或客服工单。
- 增加未成年人保护策略、举报/投诉与侵权处理流程、内容审核与违规处置机制；不鼓励上传他人未经授权的照片、私密影像或个人信息。
- 隐私政策、用户协议、付费/退款规则、创作者与平台责任边界，应由实际运营主体根据业务模式和大陆法律完成审查，不使用空泛模板冒充合规。

### 中国大陆支付与产品场景
- 目标支付方式优先评估微信支付、支付宝；不以个人收款码代替平台订单支付，也不把用户扫码或前端返回页当作支付成功凭证。
- 先确定平台究竟是自营数字服务还是撮合创作者提供服务。若平台代多位创作者收款并分账/结算，必须先取得支付机构认可的商户/服务商或平台分账方案，并落实创作者实名/资质审核、资金结算、退款、争议处理和税务安排；不得自行归集、沉淀或违规分配资金。
- 微信支付 H5 支付有特定场景和准入要求：商户官方文档说明 H5 支付用于微信客户端外的手机浏览器，并要求商户号、产品权限及已备案支付域名；微信内网页应按实际主体和产品形态评估公众号 JSAPI 或小程序支付，不要用外部 H5 跳转小程序收银台绕过场景规则。支付宝也需按实际 H5/网页/小程序场景申请相应产品能力。
- 逐关独立定价、下单、支付验签、异步通知幂等、退款和结算都必须在服务端完成；支付成功仅以支付机构验签后的服务端结果为准。未完成准入和联调前，继续保持 `PAYMENT_PROVIDER=disabled`。

### 大陆发布验收新增项
- [ ] 运营主体、业务分类和 ICP 备案/许可要求经核实，备案/许可信息可公开查询。
- [ ] 正式服务、数据库、对象存储、备份、日志和 CDN 的地域与数据流向已盘点。
- [ ] 已完成个人信息处理清单、隐私政策、用户协议、保存期限和删除/投诉流程审查。
- [ ] 境外服务商、跨境访问和数据出境风险已识别；需要的告知、单独同意及合规程序已完成。
- [ ] 境内邮件/短信/云存储服务完成真实可达性、权限、删除和安全测试。
- [ ] 微信支付/支付宝商户准入、产品场景、支付域名、创作者结算和退款机制已获批准并通过端到端验收。
- [ ] 微信内置浏览器、微信外手机浏览器、支付宝内置浏览器及常见 Android/iOS 设备均完成真实体验测试。

## 1. 服务器要求

- 支持 Docker Engine 与 Docker Compose v2 的 Linux 主机。
- 构建和运行镜像使用受支持的 Node.js 22 Alpine LTS 基础镜像。
- 建议至少 2 vCPU、2GB RAM；生产环境按流量和图片存储需求扩容。
- 一个已指向服务器的域名，以及 HTTPS 反向代理（例如由 Caddy/Nginx 终止 TLS）。
- 防火墙只开放 HTTPS 入口；不要把 PostgreSQL 端口暴露到公网。

## 2. 准备配置

在仓库目录执行：

```bash
cp .env.example .env
```

编辑 `.env`，至少将 `POSTGRES_PASSWORD` 替换为长随机密码；同时检查 `.env.example` 中所有适用变量。不要沿用示例占位值。可使用 `openssl rand -hex 32` 生成数据库密码。当前应用的登录会话令牌由服务端使用密码学安全随机数生成，并以哈希形式存储在数据库中；代码没有读取 `SESSION_SECRET`，因此模板不再提供一个未接入的伪配置项。生产部署还应设置：

- `APP_URL=https://你的正式域名`（必须与实际对外 HTTPS 地址一致，邮件验证和密码重置链接依赖它）
- `EMAIL_PROVIDER=disabled`：默认关闭邮件发送；仅在适用地区完成可达性、数据处理和合规评估后，才可显式设置为 `resend`。当前唯一实现的服务商是 Resend
- `RESEND_API_KEY`：仅当 `EMAIL_PROVIDER=resend` 时使用
- `EMAIL_FROM`：Resend 已验证域名中的发件地址
- `REQUIRE_VERIFIED_EMAIL=true`：只有在邮件发送已完成验证后再启用。**中国大陆生产上线阻断：** 当前尚未实现境内邮件/短信 provider，不能只改环境变量就切换服务商；`EMAIL_PROVIDER` 默认 `disabled`，不会因配置了 Resend 密钥而自动向境外发送邮件。必须先接入选定的境内服务商，并完成实名/签名/模板、送达率、退订/投诉及数据地域验收。在此之前不得把 Resend 当作大陆生产邮件方案，也不得启用依赖邮件的生产注册/找回流程。
- `STORAGE_ENDPOINT`、`STORAGE_PUBLIC_URL`、`STORAGE_REGION`、`STORAGE_BUCKET`、`STORAGE_ACCESS_KEY`、`STORAGE_SECRET_KEY`：需要真实照片上传时配置

不要把 `.env` 提交到 Git。生产密钥应使用服务器密钥管理能力保存，并定期轮换。

## 3. 启动应用

```bash
docker compose run --rm migrate
docker compose up -d --build
docker compose ps
docker compose logs -f app
```

Compose 会先启动 PostgreSQL，等待数据库健康检查通过，再依次执行可重复的 `db/schema.sql`、互动回应、收件箱已读状态、回应消息和逐关进度迁移，最后启动 Next.js 应用。迁移文件清单以 `docker-compose.yml` 的 `migrate.command` 为准；升级前务必核对该清单与 `db/migrations/` 中的迁移顺序一致。数据库数据保存在名为 `heart_studio_data` 的 Docker volume 中。

应用容器监听 3000 端口，Compose 默认只将其绑定到主机回环地址 `127.0.0.1:3000`，便于主机上的 Caddy/Nginx 反向代理访问。应用对所有路由设置 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy` 等浏览器安全响应头；生产环境还会发送 HSTS。生产环境应通过 HTTPS 反向代理访问，并确保反向代理正确传递 Host、协议和请求头；不要将应用端口改为公网监听。

健康检查分为两层：`GET /api/health` 只检查 Next.js 进程是否存活；`GET /api/ready` 会实际执行数据库查询，返回数据库是否就绪。部署验收时应两者都返回 HTTP 200。

## 4. 备份与升级

升级前先备份数据库：

```bash
docker compose exec -T db sh -c 'pg_dump -U heart -d heart_studio' > heart-studio-backup.sql
```

更新代码后：

```bash
git pull
docker compose up -d --build
```

恢复备份前应停止写入并确认备份文件完整：

```bash
cat heart-studio-backup.sql | docker compose exec -T db psql -U heart -d heart_studio -v ON_ERROR_STOP=1
```

备份文件可能含账户邮箱、作品私密内容和交易记录，必须加密保存并限制访问。不要把备份上传到公开仓库。

## 5. 上线验收

- [ ] 域名 HTTPS 正常，HTTP 自动跳转 HTTPS。
- [ ] PostgreSQL 未暴露公网，数据库密码为强随机值。
- [ ] Resend 发件域名已验证，实际收到邮箱验证和密码重置邮件。
- [ ] 开启 `REQUIRE_VERIFIED_EMAIL=true` 后，未验证账户不能发布作品。
- [ ] 对象存储桶权限仅允许应用服务端写入，公开读取仅开放封面对象；测试上传 JPG/PNG/WEBP/GIF，确认 8MB、2000 万像素限制、真实解码、格式核验、重编码为 WebP、EXIF 方向处理、元数据剥离及公开图片 URL。当前服务端使用 Sharp 解码后缩放并重编码，浏览器不再获得对象存储直传凭证；已增加每位创作者每分钟最多 10 次上传的数据库原子限流，并对数据库保存失败的对象执行清理尝试；仍需补恶意内容扫描、对象存储生命周期/孤儿对象巡检和跨节点压力测试。反向代理/网关必须对请求体设置不低于 8MB 加 multipart 开销、且有上限的 body-size 限制和请求超时。
- [ ] 备份和恢复演练成功。
- [ ] 隐私政策、服务条款已由运营主体补齐并完成目标市场法律审查。
- [ ] 支付机构商户准入、创作者结算安排和退款规则已获批准。

## 6. 真实支付仍未开通

当前 `POST /api/orders` 会返回 503 `PAYMENTS_NOT_CONFIGURED`。数据库里的订单约束和支付回调账本只是安全基础，不是支付渠道。必须完成支付机构/服务商准入、服务端下单、签名验签、幂等回调、退款执行和端到端验收后，才能对外收费。不得用个人收款码或虚构订单冒充平台支付。

## 7. 故障排查

- `SERVICE_NOT_CONFIGURED`：检查 `DATABASE_URL` 和数据库连接。
- 邮件接口返回 `EMAIL_DELIVERY_NOT_CONFIGURED`：检查 `RESEND_API_KEY`、`EMAIL_FROM`、`APP_URL`。
- 照片上传提示存储未配置：检查 S3 兼容存储的 endpoint、bucket、公开 URL 和凭据。
- 应用进程未就绪：检查 `curl -i http://127.0.0.1:3000/api/health`。
- 应用可响应但数据库未就绪：检查 `curl -i http://127.0.0.1:3000/api/ready`、`DATABASE_URL` 和数据库日志。
- 应用无法启动：查看 `docker compose logs app`；迁移失败时查看 `docker compose logs migrate`。

## 8. 部署前配置核对（逐项完成）

| 配置 | 何时需要 | 验收方式 |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | 始终需要 | 使用独立强随机值；确认未提交到 Git |
| `DATABASE_URL` | 应用容器内部由 Compose 根据数据库服务生成 | 检查容器运行环境指向内部数据库服务，不使用公网数据库端口 |
| `APP_URL` | 生产环境始终需要 | 与正式 HTTPS 域名完全一致；测试邮件中的链接 |
| `RESEND_API_KEY`、`EMAIL_FROM` | 启用邮箱验证、密码找回时需要 | 使用服务端密钥；发件域名已验证并收到真实测试邮件 |
| `STORAGE_*` 六项 | 启用自定义照片上传时需要 | 用正式域名完成上传、读取和删除测试；限制桶权限与 CORS，并先完成文件真实格式检测和安全处理 |
| `PAYMENT_PROVIDER` | 当前必须保持 `disabled`，直到真实支付集成完成 | `POST /api/orders` 应继续明确返回未配置状态；不要在没有验签回调和退款流程时开放收费 |

**发布前禁止项：** 不要将 `.env`、数据库备份、用户上传图片、Resend/S3/支付密钥或生产数据提交到仓库；不要把 PostgreSQL 端口暴露到公网；不要把 GitHub Pages 静态预览当作正式应用。真实支付尚未接入，不能向体验者收取平台订单款项。

## 9. 回滚与恢复演练

1. 在升级前记录当前部署的 Git commit SHA，并创建加密数据库备份。
2. 在预发布环境先执行迁移和核心流程验收；确认新版本可读写后再切换生产流量。
3. 若应用版本出现问题，回滚应用镜像到记录的上一版本；不要未经评估就回滚数据库 schema。
4. 若迁移已改变 schema，先按迁移兼容策略修复或向前迁移；只有确认备份时间点、数据损失范围和恢复影响后，才执行数据库恢复。
5. 恢复后重新检查 `/api/health`、`/api/ready`、创作者登录、分享页、关卡回应、收件箱及账户数据导出。

生产备份应定期自动化、加密并进行异地保存；至少定期做一次实际恢复演练。仅确认备份命令成功，不等于已经验证可恢复。
